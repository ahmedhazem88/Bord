# bord: Architecture Essentials

Companion to [ARCHITECTURE.md](ARCHITECTURE.md). The handful of decisions that are expensive to reverse, what changed this pass and why, and an honest red team of what's still actually wrong with the current design (v4: ground-up rebuild adding the two onboarding journeys, the Phase 2 remuneration reframing, and a fresh regulatory research pass that downgraded two rules rather than confirming them. v5, this pass: a credits-based earning model, forward-architected regulator/labor-office verification, independence-vs-representative director classification, voting-pattern conflict detection, and committee-level decision quorums).

---

## 1. Critical Decisions Only

- **Capacity as a first-class entity, decoupled from both Person and Company.** A person's identity and a person's role-at-a-company are modeled as separate records (`Person` vs. `Capacity`), not folded into a single "user" row. The single hardest-to-undo decision in the system, made deliberately up front because it's the direct product requirement (multi-capacity directors, Persona 2).
- **Postgres RLS as a second, independent tenant-isolation barrier beneath application logic.** Expensive to retrofit once data and queries exist, cheap to build in now, given FR-24's zero-tolerance status.
- **Two deliberate exceptions to tenant isolation, not one.** `NetworkProfile` (public, cross-tenant, unchanged from the prior draft) and, new this pass, the entire individual-onboarding data cluster (`Person.kyc_status`, `SelfDeclaredPosition`, `BankDetail`), which is person-owned rather than tenant-owned by design, since a person's identity exists before and independent of any company relationship. Both are one-way doors in the same sense: once a self-declared position or a public profile fact has been visible to another party, there is no clean way to retroactively make it as-if-never-shown. Adding a second exception makes the general rule ("everything defaults to strict per-company confidentiality") slightly harder to state cleanly to a new engineer, and that's a real cost worth naming, not just a design footnote.
- **Rules Engine values are versioned data (`RuleVersion` rows), never hardcoded constants**, spanning four regulators (Companies Law/GAFI, FRA, CBE, EGX). This pass adds a sharper reason to hold the line on this decision: two rules that were previously encoded with real confidence (the Art. 80 self-convening mechanism, the GA notice-period day count) had to be downgraded on re-verification. A codebase that had hardcoded either value would have shipped an unconfirmed legal assertion as if it were settled; the versioned-data model is what made the downgrade a data update instead of a code change and a redeploy.
- **AI Guidance Layer architecturally isolated from the Rules Engine**, now shared across five features (Q&A, discussion-guide generation, pre-vote conflict checking, precedent-search embeddings, and, new this pass, onboarding document extraction for both journeys). Isolating it is a bounded cost; unwinding a merged design later, under production load and with five features depending on it instead of four, is not.
- **Egypt/MENA-region data residency as a day-one infrastructure default, not a later migration.** PDPL's cross-border transfer licensing makes this a legal constraint, not a preference; individual-onboarding data (national ID, KYC results, bank details) raises the stakes on this decision rather than changing it.
- **REST/OpenAPI over GraphQL, and a modular monolith over separate services at MVP.** Both recorded as deliberate choices against a plausible alternative, both moderate-cost to reverse later if genuinely needed.
- **Remuneration data captured for Phase 2 consumability now, even though Phase 2 isn't being built.** `BankDetail` encryption standard, `PayoutExport.schema_version`, and the `line_items` bank-detail reference rather than a copy are all decisions made in this build specifically so a payment-execution layer added later doesn't require re-modeling the data it would consume (PRD Section 15). This is a real, if modest, scope commitment inside an MVP that otherwise doesn't touch payments, and it is the direct, explicit result of the user's correction on the prior draft, not an incidental design choice.
- **Credits, not cash, as the default compensation unit, gated to cash by a single platform-wide flag, new this pass.** `PlatformSettings.cash_redemption_enabled` is a one-way door in the strictest sense in this document: it is set once, by bord's own ops team, after a funding event, never by a tenant, never reversible in practice (flipping it back off after members have already redeemed cash would be a serious trust breach, even though nothing in the schema technically prevents it). The decision to make this platform-wide rather than per-company was deliberate: a per-company flag would let one customer's admin promise cash payouts before bord can actually fund them, which is a liability risk this design specifically closes off.
- **Credits are a standalone incentive ledger, confirmed explicitly over the initially-simpler alternative of folding them into remuneration.** The first design pass scoped `CreditTransaction` to remuneration only (retainer/per-meeting/committee-premium amounts). Asked directly, the requester chose the broader shape: a general governance-incentive layer, with remuneration as one source among several (meeting participation, timely resolution execution, compliance-task completion, referrals). This is the more expensive design to build (a standalone `incentives` module, nullable `companyId`/`capacityId` on `CreditTransaction` since not every earn event is company-tied) but the cheaper one to have chosen: narrowing a general incentive ledger down to remuneration-only later is a straightforward scope cut, widening a remuneration-only ledger into a general one after other modules have built against the narrower shape is a real migration.
- **Independence and conflict-detection features are advisory-only by explicit decision, not a default we happened to ship, new this pass.** `Capacity.independence_compliance_status` and `GovernanceConflictFlag` never block a vote, a resolution, or a capacity assignment. This was a direct design choice made because Egyptian regulation affirmatively defines "independent director" but not "shareholder representative" (PRD Section 5): a hard-block enforcement mechanism built on a criterion that's half-citable and half-platform-invented would be indefensible the first time a company disputes a blocked assignment. Reversing this later, to make it enforcing, is a much smaller change than the reverse (unwinding an over-enforcing feature after companies have built workflows around its blocking behavior) would be.
- **`GovernanceConflictFlag` visibility is full-board, confirmed explicitly over the initially-proposed restricted default.** The first design pass restricted read access to chairman/company_secretary/compliance_officer/system_admin, on the reasoning that a governance-conflict allegation shouldn't reach the full board before someone with authority has reviewed it. Asked directly, the requester chose full transparency instead. This is now the platform's one deliberate case of maximal disclosure over restricted disclosure for a compliance-adjacent signal, worth remembering precisely because every other similar decision in this document (bank details, KYC internals, conflict-check results) goes the other way; it is not a default this codebase should generalize from.

## 2. Resolved from Earlier Rounds

Tracked here so the record of what changed is visible, not just the current state. Items from the v1 and v3 review rounds are kept for continuity; this pass's own resolutions are in Section 2b.

- **AI reputational risk (governance-guidance feature).** Resolved with a process, not a technical fix: a mandatory pre-launch adversarial evaluation suite is a hard Phase 7 gate, tied to the same counsel relationship that owns the legal corpus. The risk itself hasn't gone away, and has grown again this pass with onboarding extraction added as a fifth AI-Layer feature, but it's a budgeted, owned line item, not an aspiration.
- **Data retention on company churn.** Resolved with an explicit interim policy: governance records retained indefinitely or a minimum of 10 years post-cancellation, pending definitive counsel confirmation.
- **Cross-tenant conflict-of-interest blind spot, partially resolved, now with a second data source.** `NetworkProfile` plus, new since v3, `SelfDeclaredPosition` from individual onboarding give the platform two legitimate ways to cross-check a director's interests: real `Capacity` records where they exist, self-declaration everywhere else. This is a real improvement in coverage (a person now declares positions proactively at onboarding, not only when building a public profile), not a full fix: it still only covers what a person actually discloses, and a false self-declaration is not detectable by the platform in any way. The blind spot is narrower and better-labeled, not closed.
- **Role-type enum rigidity.** Resolved by adding an `other` role type with a free-text label.
- **AI corpus staleness.** Resolved by tying corpus updates to the same versioned, effective-dated pattern as `RuleVersion`, on the same counsel-review cadence as the evaluation suite.
- **The member-requisitioned-meeting mechanism (FR-42).** Resolved differently than the prior draft claimed. The prior draft stated this was "now grounded in quoted statute" including a 10-day self-convening window; this pass's re-verification found only the one-third-of-directors trigger in the statute text, not the self-convening detail. See Section 2b: this is a correction, not a new resolution.
- **The GAFI/FRA person-searchable-affiliation-registry question.** Reconfirmed closed, with a new supporting detail: Egypt's Beneficial Owners Register exists but is restricted mainly to judicial officers on request, not publicly person-searchable, strengthening rather than changing the prior conclusion.

## 2b. Resolved, Corrected, or Newly Closed Out This Pass (v4)

- **The Art. 80 self-convening mechanism was downgraded, not reconfirmed, and this is a genuine correction to the prior draft, not a refinement of it.** The prior draft (v3) stated as High confidence, quoting statute, that one-third of directors could call a meeting themselves without chairman approval after a 10-day non-response window. This pass's fresh primary-text search found the one-third trigger (High confidence, reconfirmed) but could not locate the self-convening/response-window detail anywhere in Article 80's text. The honest read is that the prior draft's specific claim was likely a misremembering carried forward, not a fact that changed. The architecture responded by making `MeetingRequisition.self_convening_enabled` an explicit, off-by-default company setting rather than a hardcoded behavior, which is the right structural response, but it means FR-42 ships this build with meaningfully less legal grounding than the prior draft believed it had. Anyone reading only the PRD's Scope section, without reading Section 5's downgrade, could still walk away thinking this is settled.
- **The "100% attendance shortens GA notice to 5 days" claim was downgraded a second time, past where the prior draft already left it.** The prior draft's finding was "GAFI administrative practice, not statute," itself already a downgrade from treating it as law. This pass could not confirm even the administrative-practice framing, and instead found a plausible conflation source (an unrelated 5-day inter-newspaper-publication-gap rule). This is now the platform's most-corrected single claim across two research passes, worth flagging as a pattern: a specific, confident-sounding regulatory claim like this one traveled through at least one prior stage of the product's own history before either research pass touched it, which is exactly how an unverified detail calcifies into an assumed fact if nobody re-checks it. The process discipline that caught it (Section 18 of the PRD) is the actual mitigation, not this one claim being fixed.
- **The GA notice-period day count moved from High to Medium confidence, not because a new problem was found, but because a second source surfaced a conflict the first research pass's single-source citation had masked.** The prior draft cited Art. 202 at High confidence off one source. This pass found a second source citing Art. 203, with a conflicting day count from a third source. The statute may not have changed; the research coverage simply got less confident as more sources were checked. This is worth internalizing as a general lesson for this rules engine: a High confidence rating from a single research pass with one corroborating source is weaker than it looks, and a second pass finding a conflict should be read as "the true confidence was always lower," not "something broke."

## 2c. This Pass's Additions (v5), Stated Plainly

- **The credits model is not actually "the AfterQuery model."** Researched directly this pass: AfterQuery pays contributors entirely in cash via Stripe, with no points economy. What's built is the credits/partner-redemption/funding-gated-cash structure as separately described, confirmed with the requester before building, not AfterQuery's real model. Anyone referencing this feature internally as "the AfterQuery model" going forward is describing it by an inaccurate name; the PRD (Section 15) states this plainly so the mislabeling doesn't calcify the way the Art. 80 claim did (Section 2b).
- **The independent-vs-representative distinction is genuinely half-built by design, not by oversight.** Egyptian regulation supports a real, citable independence check. It does not support a citable "shareholder representative" check. The platform ships both as one feature with clearly different evidentiary weight, and the UI-level discipline of never presenting them as equally regulated is now a hard requirement (AGENTS.md), not a nice-to-have.
- **The committee decision-quorum feature (FR-60) has zero Egyptian legal grounding, and is labeled that way in the data model itself** (`source_citation: 'company_policy'`, not a `RuleVersion` row). This is a deliberate scope boundary: it is a company-configurable feature the platform hosts, not a compliance rule the platform enforces on the company's behalf.

## 3. Red Team (v4, v5 additions marked)

Written honestly, including the parts a founder wouldn't want to hear. Ordered roughly by how much it should worry you. Items carried from the v3 red team are kept where they remain true; new items from this pass's two onboarding journeys and the remuneration reframing are marked.

### What will break

- **The CBE rule set is still the weakest thing in this document, and this pass didn't touch it.** Every CBE-specific rule remains Medium or Low confidence, sourced from secondary reporting because CBE's own regulations library was inaccessible in both research passes now, not just one. Two research attempts failing to reach the primary source is a stronger signal than one: this may not be a research-effort problem, it may be an access problem (the circular may not be published in a generally searchable form at all), which changes the mitigation from "search harder" to "get it directly from CBE or counsel, because general web research has now failed twice." **Do not onboard a real bank customer until the primary CBE circular text and the Article 56 large-exposure regulation have actually been retrieved and reviewed by counsel.**
- **The Art. 80 downgrade (Section 2b) is a bigger deal than its one paragraph in the PRD makes it look, and this is the sharpest new risk this pass introduces.** FR-42 shipped in the prior draft's plan on the strength of a specific, quotable statutory right. That right is now unconfirmed. The product default (self-convening off) is the safe engineering response, but the business risk is different: a sales conversation, a marketing claim, or a customer's own reading of an earlier version of this documentation could still describe FR-42 as statute-grounded self-convening, because that was true as recently as the prior draft. Anyone who worked from v3's PRD or ARCHITECTURE-ESSENTIALS.md and hasn't read this v4 revision is currently carrying a wrong belief about what the law actually supports.
- **The multi-capacity remuneration calculation (FR-38) is exactly the kind of quietly-wrong logic that survives testing and fails in production**, unchanged from the prior draft's assessment, and now with higher real-world stakes: bank details are now captured (FR-52) specifically to make the export directly usable, which means a double-counting bug doesn't just produce a wrong number in a spreadsheet, it produces a wrong instruction sitting one step away from a real bank transfer once Phase 2 exists. This needs targeted test cases built from actual multi-capacity scenarios now, while the cost of a bug is still "wrong export," not later when the cost becomes "wrong payment."
- **Individual onboarding's self-declaration step (FR-51) has no fabrication control at all, and the architecture doesn't pretend otherwise, but this is worth stating as plainly as the CBE gap above.** Anyone can declare a board seat at a company that isn't a bord tenant, and nothing in the system can catch a false claim, because no external registry exists to check it against (PRD Section 5, reconfirmed this pass). The "self-declared, unverified" label is the only mitigation, and it depends entirely on a company reviewing a candidate under time pressure (Persona 3's own churn driver: low attention, few taps) actually noticing and respecting that label rather than skimming past it. This is the same shape of risk the v3 red team already flagged for `NetworkProfile`; individual onboarding makes it the default path every new user goes through, not an edge case.
- **The KYC vendor dependency is unevaluated, and it now sits on the critical path for every new user, not just company onboarding.** No vendor has been selected (PRD Section 17); Egyptian national-ID verification coverage, accuracy, and false-rejection rate are all unknowns. A high false-rejection rate on a real Egyptian national-ID format would put friction directly in front of Persona 2 (Karim), the exact time-poor persona Journey I's own friction point already worries about losing to a long form. This needs a vendor evaluation with real Egyptian test IDs before Phase 4 closes, not a vendor picked on general reputation.
- **The historical-minutes extraction step (FR-2a) is the platform's first AI-extraction feature applied to unstructured, company-specific historical documents rather than curated legal text, and it inherits every risk the v3 red team already named for the AI layer, in a harder version.** The AI Q&A and discussion-guide generator are grounded against a curated, versioned corpus the platform controls. Historical-minutes extraction runs against whatever a company happens to upload: inconsistent formatting, handwritten annotations, non-standard Arabic legal phrasing, or minutes from a period before the company had any real governance discipline. A wrong extracted fact here doesn't just risk a bad Q&A answer, it risks seeding the precedent database (the exact feature the v3 red team already flagged for false-reassurance risk) with fabricated history that then gets treated as real precedent in a future pre-vote conflict check. Human confirmation before anything is applied (FR-2/FR-2a's explicit design) is the real mitigation, but a secretary rushing through onboarding is under exactly the same time pressure that makes every other "human must confirm" control in this document imperfect in practice.
- **The pre-vote conflict check (FR-44) still raises the AI-reputational-risk stakes identified in the original review, unchanged from the prior draft's assessment.** It proactively asserts "no conflict found," which reads to a customer as the platform's one job, not as an AI being occasionally unhelpful.
- **The video SDK's roll-call fallback (FR-13) has still never been tested under its actual failure mode**, unchanged across three drafts now. Designed on paper each time; still not fire-drilled.
- **Precedent search (FR-43) carries the same false-reassurance shape flagged before, and onboarding seeding (FR-2a) changes but doesn't remove it.** A company that uploads a thin historical record at onboarding still gets a precedent index that looks populated but isn't deep, which is arguably a subtler version of the original risk: "no related precedent found" now can mean "genuinely nothing relevant," "too little history was ever logged," or "the company's historical uploads were thin and only partially extracted," and the UI still doesn't distinguish any of these three states from each other.
- **The voluntary compliance certificate (FR-48) remains a reputational risk to bord itself**, unchanged from the prior assessment: the scoring methodology still hasn't been designed, only named as a feature.
- **New this pass: the credits economy has no anti-gaming design at all.** `CreditTransaction` posts straight from `RemunerationStructure`'s attendance-based calculation, the same logic already flagged above (FR-38) as fragile under multi-capacity double-counting, now with a second consequence beyond a wrong export: a wrong credit-earning calculation is now a live balance a member can immediately spend against the partner catalog, not a static export file someone reviews before it moves money. The double-counting bug and the credits economy make each other worse in combination, and neither this pass nor the prior one has built the targeted test cases either needs.
- **New this pass, and sharper than it would otherwise be because of the full-board-visibility decision: `mislabel_incident` conflict flags will produce real false positives, with no restricted-audience buffer.** Two genuinely independent directors can agree with a shareholder representative on a resolution's actual merits without any collusion; FR-58 flags that vote pattern regardless, by explicit design (the request was to flag every incident, not wait for corroborating signal). FR-59 makes every such flag visible to the entire board immediately, a confirmed, deliberate choice (Section 1), not an oversight, but it means a false `mislabel_incident` flag is a public allegation against a named director from the moment it fires, not something a compliance officer triages first. Nothing in the current design coaches "this is a lead worth investigating, not confirmed misconduct" into the UI at the point where every board member first sees it, and that gap matters more now than it would under a restricted-visibility design.
- **New this pass: the corporate-partner catalog (FR-54) launches empty, and nothing in this build owns filling it.** `CorporatePartner` is modeled and the redemption flow works end to end, but bord has no partnerships yet (PRD Section 17). A credits economy with no live redemption catalog is a liability with no offsetting member benefit, this is a business-development dependency sitting directly on the MVP's critical path, not a build-phase risk.

### Edge cases still missing

- **What happens to an unverified shareholding's vote is unspecified**, unchanged from the prior draft: still needs a decision before FR-30 is built.
- **The `RuleVersion.company_override_id` approval workflow is still not concretely designed**, unchanged across drafts: still a stated intention, not a build-ready spec.
- **A fabricated or exaggerated self-declared candidate profile is only partially mitigated by the verified/self-declared label**, and this pass makes the gap wider, not narrower, since individual onboarding is now the default account-creation path rather than something built specifically for the network module.
- **Cross-capacity scheduling conflict detection (FR-5) still degrades to nothing the moment a director holds a capacity at a non-bord company**, unchanged: calendar sync narrows this for a connected provider but doesn't close it.
- **A discretionary committee created via FR-47's resolution-gated flow can still end up with no defined mandate**, unchanged.
- **New this pass: nothing in the onboarding design specifies what a company can see about a candidate's onboarding-completeness state during Journey G.** Can a company tell that a candidate's KYC is pending, versus verified, versus never started, before deciding whether to appoint them? The independence cross-check (Journey G step 4) assumes the candidate's declared positions are visible, but the surrounding trust-signal question (is this a real, KYC-verified person at all) isn't addressed anywhere in the current screens or API.
- **New this pass: an individual who completes onboarding but is never invited to any company has no defined product experience.** The data model supports it (a `Person` with no `Capacity` rows is entirely valid), but nothing in the PRD's journeys or the screen inventory describes what that person's Home/dashboard actually shows, whether their `NetworkProfile` is auto-published or requires an explicit opt-in, or how they're expected to discover the board-seat marketplace in the first place.
- **New this pass: what happens to a `Committee.decision_quorum` when a company changes its committee's independent-member headcount mid-cycle is unspecified.** If a committee drops below the number of independent members needed to mathematically reach a configured `min_independent_votes`, no defined behavior exists, silently unreachable quorum, an alert to the company secretary, or an automatic quorum-config invalidation are all plausible and none is chosen.
- **New this pass: `GovernanceConflictFlag`'s rolling-window threshold for the two pattern-level flag types (`consistent_split_votes`, `independent_vs_representative_opposition`) is referenced in the PRD as company-tunable but has no default value specified anywhere.** A rules-engine feature that fires on a pattern needs a starting number of resolutions and a starting time window before it can run at all; neither is decided.

### What's over-engineered

- **Nothing new is flagged as over-engineered this pass.** The prior draft's items (the three-service split, Persona 6's full portfolio-view UI) still stand as resolved or appropriately deferred. Worth actively watching, same as before: it would be easy for the onboarding cluster specifically (KYC vendor abstraction, the `ExtractedFact` review-queue UI) to accumulate premature generality, since it's new enough this pass that nobody has stress-tested it against real usage yet.

### What's under-engineered

- **No migration strategy for `RuleVersion` changes**, unchanged, and now demonstrably relevant: this pass itself produced two downgrades (Art. 80, GA notice period) that are exactly the kind of change this missing runbook would need to handle for any company already relying on the old values.
- **The network layer's moderation and dispute process is genuinely absent**, unchanged.
- **The GA module's phased-design boundary is architecturally sound but operationally thin**, unchanged.
- **`Capacity.committee_voting_member` is a one-field fix for a bigger under-specified problem**, unchanged: what a non-voting attendee actually sees and receives is still undefined.
- **The discussion-topic taxonomy (FR-46) still lacks an owner or review cadence**, unchanged.
- **Calendar OAuth consent (FR-45) is still an unaddressed UX and trust risk**, unchanged.
- **New this pass: the individual-onboarding friction point named in Journey I step 7 (a senior, time-poor persona abandoning a long form) is stated as a design hypothesis, not validated, and nothing in the current build plan tests it before Phase 6.** The four-separable-steps design is a reasonable mitigation, but it's a guess about what will actually reduce drop-off, not a finding from a real user. Phase 1's discovery interviews (PRD Section 16) now explicitly include this as something to validate, which is the right fix, but it means the onboarding UX as specified in Section 2 of ARCHITECTURE.md should be treated as a first draft to test, not a settled design.
- **New this pass: BankDetail's step-up-authentication requirement is specified as a security control but has no defined session-timeout or re-challenge-frequency value.** "A fresh MFA challenge within a short validity window" (ARCHITECTURE.md Section 8) is a real requirement without a real number attached yet; this needs to become a concrete, tested value before Phase 6, not stay a qualitative description.
- **New this pass: the credit-to-EGP rate-setting process has no owner, no cadence, and no audit workflow beyond a free-text reason field.** `PlatformSettings.credit_to_egp_rate` is a real number that determines what a member's work is actually worth once cash redemption unlocks; treating its governance as a later operational detail rather than a Phase 4 architecture decision is exactly the kind of gap that turns into a trust problem the first time a member notices the rate changed without explanation.
